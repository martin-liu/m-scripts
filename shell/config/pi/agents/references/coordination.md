# Coordination and advisory lanes

Use with the bound `agents/references/execution.md`. Planning originates a course; Review, Input and Closure assess evidence. In Pi, `oracle` normally serves all four; `planner` serves only exceptional strategic Planning. OpenCode's `oracle` serves all four. Check the actual role and assigned lane before using a result. `ORACLE_ASSIGNMENT v2` and `oracle-*` result names identify the wire protocol, not which role to launch.

The parent reads `agents/references/advisory.md` before dispatching, integrating or reusing advice or assessments, including on resume. Bind it in each advisory assignment; the adviser reads that exact reference in every lane. Execution TARGETs need no advisory reference. Only when preparing, performing, integrating or reusing a formal Review, read `agent-review/SKILL.md` and its bound `agent-review/references/review.md`. First Reviewed dispatch and every Reviewed resume load `agents/templates/reviewed_unit.md`; this does not itself require a Review. `xdev/SKILL.md` alone owns xdev lifecycle and closure; load it for either.

## Recovery and completion

- **P20** Stop unfinished work only for an authoritative non-recoverable blocker, unavailable boundary expansion/reroute or exhausted proportionate materially distinct recovery; ordinary Reviewed additionally permits Review-cap non-delivery under R16. xdev uses its progress/recovery and settlement rules, never a lifetime Review count as a stop reason. Neither route permits an impossibility claim, waiver of delivery requirements, route evasion or automatic contact.
- **P21** Inspect Reviewed/xdev background children only on completion or transport resume, never poll. For same-role/same-lane replacement, cancel active stale work and confirm it stopped; replace known terminal failed/cancelled work without another cancellation. An unreachable writer or missing dispatch receipt is not proof of termination. Reconcile before assigning unfinished scope; never start a competing writer on shared state. Never revive superseded work, cross lanes, duplicate/drop scope or integrate late superseded output; recovery cannot lower route or bypass assessment.
- **P22** Wait only on confirmed-live started work with a verifiable child/provider event that automatically resumes; unstarted work is not a wait. Preserve integrated evidence and scheduled handoffs.
- **P23** Ordinary Reviewed tasks durably bind logical task ID plus generation before dispatch; runtime ID is transport metadata. Replacements use a new generation for unfinished scope. Status is pending/running/completed/failed/blocked/cancelled/superseded, not lifecycle outcome. Resume reads exact context, pending generations and all non-superseded results; material conflicts fail closed.
- **P24** Reviewed product delivery requires a clear final independent delivery assessment under `agent-review/references/review.md`, zero pending work, integrated non-superseded results and all required validation; xdev additionally satisfies its lifecycle. Worker evidence, advice and approval markers alone never complete work. Before those conditions hold, the parent must not describe the Reviewed/xdev product or current snapshot as done, complete or ready; report 'implemented, unassessed', 'assessment deficient' or the exact outstanding condition. Defined task/transport statuses and factual completed substeps are unchanged.

For a report-only objective, integrate the requested evidence/feedback, disclose limits and finish the report. This does not deliver the product, authorize repair or close a separate open implementation objective. For Reviewed/xdev product delivery, the default sequence is: align the outcome → obtain/reuse a substantive plan if I2 requires one →
implement with targeted feedback → integrate a working end-to-end batch → run due final
checks → one whole-unit Review → one complete correction batch if needed. Repeat Review
after a usable result only for corrected or rebutted material deficiencies under R14–R15; replacement of a terminal no-result call follows P21. Apply the route's recovery/effort rules:
R16 for ordinary Reviewed, xdev progress/recovery for xdev. Do not improve an already clear
result through more assessment or obtain advice on every local edit.

## Pi parent: parallel work, long runs and recovery

Parallel readers can share stable inputs, even in a dirty checkout. For concurrent writers on a clean source, use `worktree: true`: pi-subagents 0.90.0 checks for a clean source before launch and branches from a commit, not from uncommitted bytes. With a dirty source, serialize writers unless each can use a distinct already-provisioned checkout containing the intended bytes; pass that checkout as `cwd` without requesting a managed worktree. Do not commit or stash just to fan out. Have each writer verify its checkout path and starting inputs, including relevant uncommitted changes, before writing. Assign separate ports, test databases and output paths where needed. If isolation is uncertain, serialize the affected work. Only you integrate results and write lifecycle records.

When a live child's blocking supervisor request is pushed to you, reply to that request now: `subagent_supervisor({ action: "reply", replyTo: requestId, message })`. Supply only permitted facts or an in-scope decision; if those don't resolve it, tell the same child to return partial work and name the blocker. This is a reply, not a new dispatch, WAIT or user escalation. Do not poll for requests (P21).

The 30-minute default bounds the whole run, not idle time. The child deadline and its checkpoint timer both pause while the child is blocked on a supervisor reply and resume when the blocking call ends. The headless parent's wait is separate. Using observed timings, split oversized work at verifiable handoff points; keep dependent slices sequential. For an indivisible operation set `options.timeoutMs` at launch for the expected duration plus setup and handoff. Near the limit set `options.checkpointBeforeDeadlineMs` early enough for the current tool call and a handback; this best-effort checkpoint is not an extension.

A timeout ends the child run, not the objective. After timeout or scope violation, reconcile partial work (actual edits and checks, even without a handoff) and confirm the previous writer stopped before replacement. Assign a fresh Worker only the unfinished scope; do not retry the same scope and budget unchanged. Only if inline recovery is necessary, name one authorized action and its exit condition. The next safe, separable unit goes back to Worker unless the same concrete blocker still applies.

For a same-task follow-up, use the eligible, non-superseded Worker run by ID if supported. Send only the gap and what it needs: new material and relevant accepted evidence, inline or at child-readable references. If only the parent can retrieve a missing authorized source, pass the material to Worker for analysis and credit retrieval accurately. If the prior run can't be used, reconcile under P21 before giving a fresh Worker a self-contained TARGET for just the gap. Independent assessments always start fresh.

On resume, reuse supported plans and bounded results under their recorded role, lane, assignment and generation. Reconcile outstanding runs and previously consumed handoffs; a rename, new snapshot or missing receipt is not cause to relaunch. Replace only unfinished scope after confirming the prior run is terminal or cancelled and stopped. Use the same lane and a linked new generation under P21; preserve lineage, findings and Review expenditure. Integrate a usable recovery plan and take its first applicable action.

## Decisions and contact

- **I2** On Reviewed/xdev, obtain or reuse source-first Planning before dependent implementation when substantive goal interpretation, architecture, strategy, decomposition or validation design remains unsettled; Direct retains its bounded no-strategic-Planning route and reroutes if that boundary changes. Group related questions into one coherent plan with actions and reconsideration triggers; a valid existing Planning result suffices, but a parent-authored design/default alone does not settle substantive work. Parent preference, equivalent routine implementations, execution, targeted validation and actionable repair need no call. Reconsult only when material new evidence invalidates the selected course, a substantive decision remains unresolved or R15 requires a changed strategy not supplied by prior advice; accumulate nonblocking questions for the next coherent boundary, not every fix/snapshot.
- **I3** Technical, implementation, strategy, architecture and ordinary product/UI choices, including uncertainty and “is this in scope”, are agent-owned. Exactly three user-owned kinds exist: required protected authorization; indispensable user-only access/fact with no reasonable compliant substitute; genuinely incompatible product-intent readings changing the expected outcome, not valid implementation tradeoffs. For a user-only input, ask only for the missing original fact, source or permitted reference. The agent owns the investigation and evidence write-up. If no user-owned input is missing, report the evidence gap rather than asking.
- **I4** Before any user question, check instructions/grants, obtainable evidence and authorized alternatives; obtain the actual fenced matching `USER_INPUT_REQUIRED` input record from a completed Oracle run witnessed starting in the current request epoch. Only this record permits asking, never execution or closure. Do not defer required work behind implied or future/conditional confirmation, readiness ratification or a go-ahead; such a dependency uses this gate just like an explicit question.
- **I5** For ordinary indispensable blockers, finish other feasible authorized work and permitted preparation first; deduplicate dependency/question and ask only when no authorized work remains ready. Initial outcome alignment follows I7 before dependent implementation, not after completing unrelated sprints. Targets, baselines, test plans, failed checks, unavailable assessment, uncertainty, disabled continuation and exhausted effort alone permit no contact.
- **I7** Initial goal clarification is one question in one user turn per objective, only for irreconcilable outcome readings after proportionate discovery and bounded intake preparation. Resolve indispensable high-level ambiguity at intake, before dependent implementation or long-running work; the I4 input assessment is still required. Use purpose goal-clarification and kind product-intent; never a menu/questionnaire or a choice among valid implementations. Resume, compaction, generations and assessment failures do not reset it; only a materially replaced objective does.
- **I8** Never reopen a clear goal. An inadequate/partial reply neither authorizes guessing nor repeats the unchanged question; use resolved facts and retain dependencies. Re-ask only through the ordinary indispensable-blocker gate with materially new grounds or a narrower item, never waiving required authorization/access/fact questions.
- **I9** Only the parent emits `USER_QUESTION: <exact question>` once, verbatim from the record, in its final message. Pi user BLOCKED binds the same oracle run and dependency; Oracle carries the question only in JSON. Contact permission is not permission to abandon other ready work.
